Decisiones que sostienen el diseño

  • Bloqueo de fila: SELECT … FOR UPDATE sobre la cancha serializa las reservas; 30 peticiones simultáneas producen exactamente 1 reserva.
  • Idempotencia en la creación de reservas con clave persistida y repetición del mismo resultado.
  • Trabajos programados cada 60 s: expiración del bloqueo de pago y cierre de reservas concluidas.
  • Montos en BigDecimal y fechas UTC explícitas, con America/Lima en el borde de la interfaz.

Flujo crítico: reserva concurrente

  1. Validar sesión, ventana de anticipación y duración de la franja.
  2. Abrir transacción InnoDB y bloquear la fila de la cancha.
  3. Revalidar estado del establecimiento, horario, bloqueos y solapes.
  4. Bloquear la cochera, si aplica, en orden consistente cancha → cochera.
  5. Calcular la tarifa con promoción y cochera; guardar el importe histórico.
  6. Insertar reserva, historial e idempotencia; confirmar.
  7. Fuera del bloqueo: pago simulado determinista y transición de estado con aviso interno.

El mismo protocolo se usa al confirmar, rechazar, reprogramar, cancelar y bloquear franjas, de modo que ningún camino pueda crear un solape.

1.1 Arquitectura general y recorrido de una petición

Una petición de reserva atraviesa cuatro fronteras: el navegador, el borde web, el servidor Quarkus y la base de datos. Cada frontera tiene una responsabilidad distinta y un contrato explícito. El navegador nunca habla con MySQL; el servidor nunca confía en lo que envía el navegador; la base no conoce reglas de negocio.

Cliente

Angular 22 renderiza la interfaz, mantiene el estado de sesión y llama a la API. No calcula precios ni decide si una franja está libre.

Borde

Nginx entrega la aplicación y reenvía /api al servidor. Evita CORS en producción y centraliza el punto de entrada.

Servidor

Quarkus recibe HTTP, valida el token, ejecuta el caso de uso y aplica las reglas. Un solo proceso contiene los 12 módulos.

Datos

MySQL conserva el estado; InnoDB aporta transacciones y bloqueo por fila. Flyway es el único que modifica el esquema.

1.2 Arquitectura hexagonal: puertos, adaptadores e inversión de dependencias

La arquitectura hexagonal no es un dibujo de capas: es una regla de dependencias. El dominio define qué necesita mediante interfaces (puertos) y la infraestructura las implementa (adaptadores). La flecha de dependencia apunta siempre hacia dentro: el dominio no importa Quarkus, JPA, HTTP ni MySQL.

Estructura real de un módulo 
bookings/
├── domain/
│   ├── model/Reserva.java
│   ├── model/FranjaHoraria.java
│   └── model/CocheraReservada.java
├── application/
│   ├── port/in/ReservasUseCase.java
│   ├── port/out/ReservaRepositorio.java
│   ├── service/CrearReservaService.java
│   └── dto/CrearReservaCommand.java
├── adapter/in/rest/ReservaResource.java
└── adapter/out/persistence/
    └── ReservaPersistenciaAdapter.java

El paquete domain solo contiene Java: agregados, value objects y reglas. Las anotaciones de framework viven en application y adapter.

Ejemplo concreto: al crear una reserva, el servicio de aplicación recibe un comando, construye la franja, pide al puerto que bloquee la cancha y valida las reglas del dominio. No sabe si detrás hay MySQL, un mock de prueba o una base en memoria. Cambiar el adaptador no cambia una sola línea de Reserva.

Regla verificada: ArquitecturaTest falla si domain importa jakarta.*, io.quarkus.* u org.hibernate.*, o si un módulo importa entidades JPA de otro. La separación no depende de la disciplina del equipo: la comprueba la suite.

1.3 Monolito modular: doce módulos, un solo proceso

CanchaDirecta es un monolito modular, no un conjunto de microservicios. Hay un solo artefacto desplegable y una sola base de datos; los módulos se llaman por puertos en memoria. Esa decisión evita transacciones distribuidas en el flujo más delicado —reservar una franja— y mantiene la posibilidad de extraer un módulo si algún día lo exige la escala.

1.4 Quarkus frente a Spring Boot

Los dos frameworks resuelven el mismo problema: exponer una API, inyectar dependencias, persistir con JPA y ejecutar reglas dentro de una transacción. La diferencia está en el modelo de ejecución, en las convenciones y en el peso del runtime. Esta comparación es conceptual: CanchaDirecta sigue usando Quarkus y no hay una migración prevista.

1.4.1 Ocho ejemplos equivalentes

Cada par muestra el mismo concepto, no una migración. Los ejemplos de Quarkus siguen el estilo del proyecto; los de Spring Boot son equivalentes idiomáticos.

A · Consultar una reserva por id

Spring Boot
// Spring Boot
@RestController
@RequestMapping("/api/v1/reservas")
class ReservaController {
    private final ReservaService service;
    ReservaController(ReservaService service) { this.service = service; }

    @GetMapping("/{id}")
    ReservaResponse ver(@PathVariable Long id,
                        @AuthenticationPrincipal UsuarioActual user) {
        return service.ver(id, user.id());
    }
}
Quarkus
// Quarkus
@Path("/api/v1/reservas")
@Authenticated
public class ReservaResource {
    @Inject ReservasUseCase reservas;
    @Inject JsonWebToken jwt;

    @GET @Path("/{id}")
    public ReservaResponse ver(@PathParam("id") Long id) {
        return reservas.ver(id, Long.valueOf(jwt.getSubject()));
    }
}

Ambos exponen el mismo contrato. Spring toma el usuario del contexto de seguridad; Quarkus lo toma del sub del JWT. En los dos casos el id del titular no se acepta desde el cuerpo.

Spring puede derivar la consulta del nombre del método; Quarkus mantiene el puerto en el dominio y el SQL en el adaptador. La segunda forma hace explícita la frontera y permite probar el caso de uso con un doble.

1.5 Persistencia, concurrencia y ciclo de vida

MySQL 8 con InnoDB es la única fuente de verdad. El esquema tiene 44 tablas y 18 migraciones Flyway; Hibernate solo valida que las entidades coincidan, nunca crea ni borra tablas. Los adaptadores de persistencia usan SQL nativo cuando la operación necesita control explícito de bloqueo, tipos o columnas generadas.

Transacción

Cada caso de uso crítico abre una transacción InnoDB. Si falla una validación, no queda una reserva a medias ni un pago huérfano.

Bloqueo

SELECT … FOR UPDATE sobre la cancha serializa las peticiones. La cochera se bloquea después, en orden consistente, para evitar deadlocks.

Idempotencia

La clave se guarda con la reserva. Un reintento devuelve la misma reserva en lugar de crear otra.

La creación termina en PENDIENTE. El pago se procesa después, en otra transacción, y registra un pago aprobado; no cambia el estado de la reserva por sí solo. La confirmación la realiza el propietario o la administración, o el cobro presencial de recepción.

La prueba de concurrencia E-08 lanzó 30 peticiones al mismo bloque: exactamente una obtuvo 201 y las demás recibieron 409. El bloqueo no se apoya en un trigger ni en una validación aplicativa sin transacción; la garantía está en la fila bloqueada y en el commit.

Tres piezas que conviene entender

Quarkus: el servidor

No es un servidor de aplicaciones pesado. Analiza el código al compilar, genera solo lo que se usa y arranca en segundos; por eso puede correr en un contenedor pequeño. Aporta las piezas de siempre —inyección de dependencias, configuración, HTTP, validación— con menos memoria y sin archivos XML.

Angular standalone, signals y zoneless

Standalone elimina los módulos: cada componente importa lo que necesita y se puede cargar por área. Un signal es un valor que avisa a la vista cuando cambia; con zoneless Angular deja de revisar toda la aplicación tras cada evento y actualiza solo lo que depende de ese valor. Menos trabajo, comportamiento más predecible.

Flyway: la base como historial

En lugar de crear tablas a mano, cada cambio queda en un archivo SQL con número. Flyway registra cuáles se aplicaron y ejecuta solo los nuevos. Así una instalación desde cero y una base existente terminan exactamente igual, y cualquier cambio se puede revisar en Git.

El servidor hereda del BOM de Quarkus; la interfaz fija Angular 22 y Node 24 en el Dockerfile.

Fronteras explícitas

La pasarela de pago está detrás de un puerto y hoy la implementa un simulador determinista, reemplazable sin tocar reservas ni liquidaciones.

Arquitectura y datos

Monolito modular
Una sola aplicación desplegable, dividida en módulos con límites explícitos. Comparte proceso y base de datos; no es un conjunto de microservicios.
Arquitectura hexagonal · ports and adapters
El dominio define interfaces (puertos) y la infraestructura las implementa (adaptadores). Permite cambiar base de datos, pago o correo sin tocar las reglas de negocio.
Capa
Nivel con una responsabilidad: presentación (interfaz), aplicación (coordina casos de uso), dominio (reglas) e infraestructura (persistencia y servicios externos).
DTO · data transfer object
Objeto plano que transporta datos entre capas o por HTTP. Evita exponer las entidades internas y acoplar la API al modelo de base de datos.
ORM · JPA
El ORM traduce objetos Java a tablas; JPA es el estándar de Java y Hibernate su implementación. Aquí se usa para leer y escribir, mientras Flyway posee el esquema.
Migración
Archivo SQL numerado que transforma el esquema de forma ordenada. Flyway registra las aplicadas y ejecuta solo las pendientes.
ACID
Propiedades de una transacción: atomicidad (todo o nada), consistencia (respeta reglas), aislamiento (no se mezcla con otras) y durabilidad (lo confirmado permanece).
InnoDB
Motor de almacenamiento de MySQL con transacciones, claves foráneas y bloqueo por fila. Es lo que permite reservar sin solapes.
Tercera forma normal · 3FN
Diseño relacional donde cada dato depende de su clave y no hay dependencias transitivas. Evita duplicados e inconsistencias.
Bloqueo pesimista
Bloquear la fila antes de operar para que otra transacción no la modifique al mismo tiempo. Se usa sobre la cancha para serializar reservas.
Idempotencia
Repetir la misma petición produce el mismo resultado y no duplica el efecto. Protege ante reintentos de red o doble clic.
Importe histórico · snapshot
Copia del precio y las condiciones al momento de reservar. Un cambio posterior de tarifa no altera el comprobante ya emitido.
DDL y DML
DDL define estructura (crear o alterar tablas); DML manipula datos (insertar, actualizar, borrar). El proyecto separa los usuarios que pueden hacer cada cosa.
Healthcheck
Comprobación de salud que indica si el servicio ya está listo para recibir tráfico. Docker la consulta antes de enviar peticiones.

Plataforma y seguridad

Quarkus
Framework Java que analiza la aplicación al compilar, genera solo lo necesario y arranca en segundos con bajo consumo de memoria. Aporta inyección de dependencias, configuración, HTTP y empaquetado.
BOM · bill of materials
Lista de versiones compatibles de un conjunto de librerías. Al heredar del BOM de Quarkus, todas las piezas se actualizan de forma coordinada.
JWT · JSON Web Token
Credencial firmada que el cliente envía en cada petición. Contiene identidad y roles, no datos sensibles, y el servidor puede validarla sin guardar sesión.
HS256
Firma simétrica HMAC con SHA-256: el mismo proceso firma y verifica con una clave local. Es suficiente para un monolito; no permite que un servicio externo valide el token sin compartir la clave.
JWKS
Punto donde se publicarían claves públicas si se usara firma asimétrica. CanchaDirecta no lo expone: la clave vive en .secrets y se monta en el contenedor.
RBAC · role-based access control
Control de acceso por roles: usuario, propietario, recepción y administrador. Cada rol ve y modifica solo lo que le corresponde.
BCrypt
Algoritmo de hash lento y con sal para contraseñas. Guarda un resumen irreversible; no se puede volver a la contraseña original.
TLS · HTTPS
Cifrado del canal entre navegador y servidor. Evita que credenciales o datos personales viajen legibles por la red.
PCI DSS
Estándar de seguridad para datos de tarjetas. No aplica aquí porque no se almacenan ni procesan números de tarjeta: el cobro es simulado.
OpenAPI · Swagger
OpenAPI describe la API (rutas, parámetros, respuestas) en un contrato estándar; Swagger UI lo muestra como documentación interactiva.
Nginx · proxy inverso
Servidor web que entrega los archivos de la interfaz y reenvía las llamadas /api al servidor de aplicaciones.
Docker multi-etapa
La imagen se construye en etapas: una compila y otra copia solo el artefacto final. Resultado: imagen pequeña, sin herramientas de compilación y sin usuario root.
Variables de diseño · design tokens
Valores con nombre (color, espacio, tipografía) definidos una vez y reutilizados. Cambiar un token cambia todo el sistema sin tocar cada componente.
ARIA · aria-live
Atributos que describen la interfaz a las tecnologías de asistencia. aria-live anuncia cambios importantes, como un aviso o un error.

Interfaz y accesibilidad

SPA · single page application
Aplicación que carga una vez en el navegador y navega sin recargar la página. El enrutador cambia la vista y solo pide datos a la API.
Standalone
Componente Angular que declara sus propias dependencias, sin un módulo contenedor. Facilita la carga por área y reduce el acoplamiento.
Signals
Valor reactivo que notifica a la vista cuando cambia. Sustituye el recorrido constante del árbol por actualizaciones puntuales.
Zoneless
Angular sin zone.js: la detección de cambios se apoya en signals y no en interceptar todos los eventos del navegador.
CDK · Component Dev Kit
Piezas de Angular sin estilo: diálogos, overlays, listas y navegación por teclado. Aportan comportamiento accesible y dejan el diseño en manos del proyecto.
Lazy loading
Cargar el código de un área solo cuando el usuario entra en ella. Reduce el peso inicial y acelera la primera pantalla.
Foco atrapado · focus trap
Mientras un diálogo está abierto, la tecla Tab no sale de él. Al cerrarlo, el foco vuelve al botón que lo abrió.
WCAG 2.2 AA
Pautas de accesibilidad para contenido web. El nivel AA exige contraste suficiente, teclado completo, foco visible y nombres accesibles, entre otros criterios.
Primero móvil · mobile-first
Diseñar desde la pantalla más pequeña (360 px) y ampliar hacia escritorio, en lugar de reducir una vista grande.
Estado vacío, de carga y de error
Vistas explícitas para cuando no hay datos, se está esperando o algo falló. Evitan pantallas en blanco y comunican qué puede hacer el usuario.

Proceso, pruebas y gestión

WBS · EDT
Estructura de desglose del trabajo: divide el proyecto en paquetes y actividades numeradas. En el cronograma va de 1.1 a 8.3.
BPMN
Notación gráfica de procesos de negocio. Usa carriles por responsable, compuertas de decisión y eventos de inicio y fin.
ADR · architecture decision record
Registro breve de una decisión de arquitectura: contexto, alternativas, elección y consecuencias. El proyecto tiene 48.
RF y RNF
Requisito funcional: qué debe hacer el sistema. Requisito no funcional: cómo debe hacerlo (rendimiento, seguridad, usabilidad, disponibilidad).
Caso de uso · actor
Interacción entre un actor (usuario, propietario, administrador, pasarela) y el sistema para lograr un objetivo.
Include y extend
En casos de uso, include es un paso obligatorio que siempre ocurre; extend es una variante opcional que solo se ejecuta en ciertas condiciones.
Prueba de humo · smoke test
Recorrido rápido de extremo a extremo para detectar fallos gruesos antes de probar a fondo. Aquí son 153 verificaciones sobre la API.
E2E · extremo a extremo
Prueba que recorre un flujo completo en un navegador real, desde el acceso hasta el resultado final.
CI · integración continua
Cada cambio se compila y se prueba automáticamente en un entorno limpio. Detecta rupturas antes de que lleguen a la entrega.
Prueba de carga
Simula muchos usuarios concurrentes para medir tiempos de respuesta y errores. Es la que falta para declarar el requisito de 50 usuarios.
Hito · milestone
Punto de control con fecha, sin duración. En el cronograma son M1 a M4, uno por mes de ejecución.
Criterio de aceptación
Condición verificable que debe cumplirse para dar una entrega por cerrada. Se documenta junto con su evidencia.

Arquitectura, frameworks y diagramación

Puerto
Contrato que define el núcleo: qué necesita o qué ofrece, sin decir cómo se implementa. ReservasUseCase y ReservaRepositorio son puertos.
Adaptador
Implementación concreta de un puerto. ReservaResource adapta HTTP; ReservaPersistenciaAdapter adapta SQL.
Inversión de dependencias
El núcleo no depende del framework: define una interfaz y la infraestructura la implementa. La flecha de dependencia apunta hacia el dominio.
Microservicios
Varios procesos desplegables por separado, con su propia base o contrato de red. CanchaDirecta no los usa: es un monolito modular.
Concurrencia
Varias peticiones compiten por el mismo recurso. Aquí se resuelve con transacción, bloqueo de fila, restricción única e idempotencia.
Spring Boot
Framework Java con convenciones y ecosistema amplio. Se usa en este documento como comparación conceptual; el proyecto no lo emplea.
Guard
Función del router Angular que decide si se entra a una ruta. Mejora la experiencia; no reemplaza la autorización del servidor.
Interceptor
Función que envuelve una petición HTTP. Aquí adjunta el token, renueva la sesión y normaliza errores.
C4
Modelo para describir arquitectura en cuatro vistas: contexto, contenedores, componentes y código.
UML
Lenguaje de diagramas: clases, secuencia, estados, casos de uso y despliegue.
CanchaDirecta

Reserva de canchas deportivas en Lima. Monolito modular, API REST versionada, base relacional y experiencia multiperfil.
